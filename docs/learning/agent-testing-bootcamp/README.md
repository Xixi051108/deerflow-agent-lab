## 入门课：给 DeerFlow 增加两个业务查询工具

**执行顺序已调整：先按 [原版页面启动说明](LOCAL_RUN.md) 体验真实对话，再沿这次请求理解链路，最后启用下方二次开发工具。** 参考工具的离线验证不能替代原版运行基线。

你已选择：先用合成业务任务数据，重点学习工具接入与自动化测试。

```text
原有 DeerFlow 聊天页面
  → Gateway 接收请求 / RunManager 管理运行
  → run_agent 执行已装配的主 Agent
  → 模型选择 query_task_status
  → 返回任务状态与错误码
  → 模型选择 lookup_error_code
  → 返回错误说明与排查建议
  → 原有流式响应显示到聊天页面
```

新增的是两个工具及其可选配置；请求、模型、编排、状态、工具错误处理和流式 UI 都复用项目已有实现。合成任务不等于 DeerFlow 自身的 run；此功能不查询生产系统、不执行修复。

### 先理解四个对象

| 对象 | 在本课中的例子 | 谁负责 |
| --- | --- | --- |
| 用户需求 | “任务 T1001 为什么失败？” | 你定义需求和验收标准 |
| 模型决策 | 选择工具名，并提供 `task_id` 参数 | DeepSeek 等已配置模型 |
| 工具执行 | 从本地合成 JSON 数据返回事实 | 我们新增的 Python 工具 |
| 自动化测试 | 断言 T1001 是 failed，错误码为 E_TIMEOUT | pytest；不需要真实模型 |

`config.yaml` 中的 `use` 路径把 Python 工具接入 DeerFlow；`get_available_tools()` 加载它；主 Agent 把工具 schema 提供给模型。schema 是工具名、说明和参数结构，不是把函数源码发给模型。

### 实际改动与阅读顺序

1. `backend/tests/test_task_diagnosis_tools.py`：先看一个输入和对应的明确预期。
2. `backend/packages/harness/deerflow/community/task_diagnosis/tools.py`：查看工具参数、固定数据读取、返回结果。
3. 根目录 `config.example.yaml`：搜索 `task-diagnosis`，查看可选接入配置。
4. `backend/packages/harness/deerflow/tools/tools.py` 的 `get_available_tools()`：找到 `resolve_variable()`，理解配置如何加载为工具对象。
5. `backend/packages/harness/deerflow/agents/lead_agent/agent.py`：找到调用 `get_available_tools()` 和 `create_agent()` 的位置。

## 带练方式

主旨是发现问题、解决问题：需求缺口、可复现缺陷、环境阻碍都可以成为学习任务；先收集证据，分清根因，再做最小修改和回归。已有功能足够解决问题时不额外添加功能，不为绿灯直接跳过失败测试。

每次先布置一个完整板块：说明业务问题、所在链路、开发任务与验收 → 用户连续实现、测试与排错 → 完成后集中讲注意事项、设计取舍和面试追问 → 用户闭卷解释。卡住时给提示，不要求每写几行就停下等待；后端在板块内逐项先失败测试再实现。需要完整参考时明确标注参考代码。

“测试通过”证明当前断言成立；你能独立变更需求、排查失败并解释取舍，才算形成能力。真实模型没有运行时记录“未运行”，不要把离线模型替身的输出当作模型能力结果。
