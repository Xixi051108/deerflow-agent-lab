# 板块四：候选发现与比较维度规划

日期：2026-10-20。本块实现范围见 [任务书](RESEARCH_DISCOVERY_PLAN.md)，实际测试、真实模型问题与回归限制见 [测试报告](RESEARCH_DISCOVERY_TEST_REPORT.md)。

## 本块解决什么

确认范围后，原 DeerFlow 研究 Agent 现在获得候选发现与比较规划指引，并可将候选、排除原因、配置、动态维度、发现来源和缺口保存到同一份研究快照。支持开放品类、指定名单和指定对象加自动补充，不依赖手机／电脑白名单。

这是竞品研究应用的发现与规划能力，不是完整选购报告。当前价格、具体参数的语义核实、运行预算、报告与面板仍归板块 5–8。候选表示拟比较对象，不代表已验证满足全部购买条件；阶段仍是 awaiting_confirmation／recording，不新增“完成”状态。

## 原链路如何执行

沿用 `research_enabled: true` 的专用 Agent 配置与原确认卡。用户确认后，原模型循环执行检索、必要页面读取、规划写入和回读。所有新普通文字仍先使确认失效，范围实质变化会清除旧结果指针。

`research/planning.py` 提供固定指引和纯函数 `validate_research_plan(scope, result, batch)`。中间件在现有 `apply_batch` 合并成功后、`save_result` 写文件之前调用它；失败返回原 error.code／field／message，不推进 revision、checkpoint 或快照。原工具权限、版本校验、异步文件线程及 HTTP/SSE 路径保持有效。

指引经原研究中间件进入系统消息，`skills: []` 也能生效。用户范围、产品、理由和来源文本保持为不可信数据，不插入系统规则。普通 Agent 不注入研究指引。Gateway 原工厂和内嵌客户端使用同一中间件，不新增服务、REST 接口或 Agent 循环。

本阶段指引要求只提交 products／configurations／dimensions／sources／gaps，事实抽取和引用核对留到下一阶段；底层通用数据工具仍支持板块三全部集合，没有为了样例放宽引用或价格规则。

## 数据与写入规则

Product 新增两个可选字段，其他内容复用板块三契约：

| 字段 | 用途 |
| --- | --- |
| scope_name | 绑定当前范围里用户给出的原始指定／排除名称；允许规范产品名与用户简称不同 |
| discovery_source_ids | 指向该产品的发现来源；不能悬空、跨产品或重复 |
| reason（原字段） | 新增／更新产品的入选或排除理由，不能只含空白 |
| Dimension.description／basis（原字段） | 新增／更新维度说明与用途的关系及比较口径，不能只含空白 |
| Gap（原集合） | 保存价格、配置、硬条件、检索失败和候选不足等缺口 |

规则：

- 合并结果中 candidate 数量不能超过本次确认目标；excluded、配置和店铺来源不计为候选名额。
- 不允许自动发现时，candidate 必须通过名称精确匹配或 scope_name 绑定指定名单；明确排除对象不能成为候选，不填绑定也不能绕过名称精确排除。
- scope_name 必须属于当前指定／排除名单；明确名为 A 的对象不能重新绑定 B。同一指定名称、相同规范名称或明确相同品牌／型号不能重复占名额，Pro 等型号后缀不会被删除。
- 自动发现对象需要关联可用来源及实际返回文本。搜索摘要只作发现线索，用 kind=other，不能伪装成已读取官网。原来源适用范围规则仍须满足。
- 用户指定对象可先无来源保存，但必须说明待核实；不通过制造 URL 来满足结构要求。
- 候选不足允许部分写入，不在中间批次强制要求达到目标。最终受控样例检查数量不足说明；没有新增程序化的阶段完成判定。

scope_name 由模型填写，程序验证绑定属于名单，不能自动识别所有别名或证明绑定的真实身份。发现来源的引用关系也不能证明 URL 确实被工具返回，或理由完全受原文支持；需对照调用轨迹、固定样例和后续采集证据。hard_constraints 等自由文本没有变成通用规则引擎。

理由和缺口也可能产生幻觉，不能只核查 Claim。真实模型首轮就出现了理由写入错误电池容量、缺口捏造用户内存要求的问题；本块补了对应评测断言及证据指引，详见报告。通过这些样例不等于已杜绝同类错误。

## 旧数据与故障行为

两个新字段默认 None／空元组，schema_version 保持 1。旧快照按原始字节和哈希加载，不重写或迁移；新理由、来源和维度要求作用于新增／更新记录，名单、数量及已有关联在合并结果上检查。旧结果不符合当前写入边界时明确报错，不能静默丢记录。

原快照大小、分页读取、所有者隔离、取消及未引用文件规则继续有效；没有增加垃圾回收、索引旁路或前端状态副本。`counts.products` 包含 candidate 与 excluded，不能把它直接当成有效候选数量。

## 如何验证模型行为

`backend/tests/support/research_discovery_samples.py` 提供合成手机／笔记本页面。确定性原图测试使用脚本模型，只证明工具与存储链路；真实模型测试只替换搜索和页面边界，由已有 DeepSeek 自主提出范围、调用工具、筛选和规划。

显式运行单个实时模型测试模块（从 backend 目录，使用已有虚拟环境）：

```powershell
$env:PYTHONDONTWRITEBYTECODE = "1"
$env:DEER_FLOW_RUN_LIVE_TESTS = "1"
$env:DEER_FLOW_RESEARCH_EVAL_OUTPUT = "D:\deerflow-agent-lab\.deer-flow\local-dev\research-discovery-verification\manual-live"
& .venv/Scripts/python.exe -B -m pytest tests/test_research_planning_live.py -q --tb=short
```

该命令会真实调用现有 DeepSeek 并产生用量。每例最多 10 次模型调用、12 次工具调用、180 秒总时限；每请求 45 秒超时、不重试供应商请求，输出上限每次 3,000 tokens。输出目录只保存业务消息、工具调用、快照和用量，不序列化模型对象或密钥；省略输出环境变量时使用 pytest 临时目录。

图节点步数上限为 64，用于容纳确认、中间件与工具节点；它不是模型调用次数。测试中间件独立限制真实调用次数，避免把增加测试图节点空间当成放宽调用预算。上述保护仅存在于测试，业务范围里的限制仍未执行。

固定资料中的手机正确结果是保留两款全新机、排除仅二手机；笔记本只保留 1.35kg 的笔记本，排除台式整机与 2.6kg 的笔记本，并记录不足 2 款；仅指定名单时不补入名单外产品。自动断言检查这些样例的已知错误，仍需逐项审查理由、来源、维度、缺口和最终文字。

## 集中复盘

- **为什么不是只写提示词？** 提示词指导模型提出规划；真正保存之前，代码会拒绝数量、名单、版本或关联不合规的数据。
- **为什么仍要真实模型？** 脚本模型可以按剧本发出完美参数，无法暴露数字幻觉、捏造需求、错误引用和重复修正。真实三轮轨迹实际暴露了这些问题。
- **为何不放宽契约让模型“通过”？** 未知值的引用、价格口径错误应被拒绝。本阶段缩小提交集合，避免过早提取事实，不放松数据边界。
- **为什么不统计全网召回率？** 当前只有冻结的有限资料集，正确答案和排除条件来自样例，不具备全市场候选全集。
- **程序测试与质量检查分别证明什么？** 前者证明确定性规则和原链路行为；后者证明指定模型在这些具体资料与范围下的实际表现，不能推导全品类稳定性。

每个结果以 [测试报告](RESEARCH_DISCOVERY_TEST_REPORT.md) 的实际执行记录为准，不用历史通过数或单轮模型通过率代替最终质量结论。
